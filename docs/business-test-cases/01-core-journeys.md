# 第一层：核心业务闭环（P0）

先看 [完整用例树](README.md#1-测试用例树状图同时为推荐执行顺序)、[共用数据](00-test-data.md) 和 [自身打点要求](09-self-observation.md)。仅用NeoCat自身操作作为业务数据源；缺少打点时登记前置缺口，不另建演示业务服务。各步骤都要验收，不用后续页面出现数据替代前序正确性。全部待执行。

## K01 首次开通平台并建立测试主体

**目的**：让管理员和普通用户具备真实使用平台的基础条件。**追溯**：链路1、2、3、5、7、8。

**前置与数据**：专用未初始化环境；DS-ROLE 的账号及组织；平台时区 Asia/Shanghai；临时口令与改密口令分别准备。已有初始化环境只复用其真实时区并记录差异，首次开通子项另留待测，不重置已有平台。

**业务步骤**：
1. 打开平台首页；未初始化时应自动进入“首次开通 NeoCat”。选择平台时区，填写首个超管账号 `it.super`、初始口令和确认口令，点击“确认初始化”。如出现状态查询失败，先点击“重试”恢复检查，不在登录页猜测初始账号。
2. 开通成功后进入登录页，看到初始化成功提示，用刚创建的超管账号登录，并按提示填写当前、新口令完成首次改密。已有初始化环境从正常登录开始，不再次开通。
3. 点击“账号管理”，依次创建 `it.admin`、`it.dev`、`it.parent`、`it.multi`、`it.outsider`、`it.receiver`，然后由超管授予 `it.admin` 管理员角色。
4. 各新账号分别登录并完成首次改密，再退出；不要混用会话。
5. 用管理员打开“组织树”，创建研发中心及订单组、支付组，再创建独立组；按 DS-ROLE 加入对应成员。
6. 由 `it.dev` 进入大盘列表确认订单组可选，再由非成员 `it.outsider` 查看同一入口。
7. 重新打开平台配置、账号列表与组织树，核对保存后的状态。

**功能预期**：未初始化自动进入开通页，查询失败显示错误与重试而非直接登录；初始化后能登录并强制改密，不自动登录。已初始化访问开通页返回登录，不重新创建超管。管理员可管账号/组织；成员只看到有资格的叶子。缺失或异常入口登记缺陷，不能用后台代办冒充该步骤完成。

**数据预期**：一份固定时区档案、七个字符串账号标识；角色为一个SUPER_ADMIN、一个ADMIN、五个USER；凭据非明文。慢阈值1000/100/1000/50ms，三个通道初始未配置；组织树和成员路径与 DS-ROLE 一致，无多余大盘/规则。初始化本身只创建超管，其他六账号来自步骤3。

## K02 自身组织查询 → 上报 → Transaction → 取样 → Trace

**目的**：验证监控平台最核心的请求定位闭环，而不是只验证“上报已接收”。**追溯**：链路11、13、16、17。

**前置与数据**：K01测试主体就绪；NeoCat自身URL打点及SDK真实传输可用，覆盖认证拒绝；准备DS-TX的实际请求台账，保留本地树标识；正常负载且本次取样保留。双实例为同一平台构件，缺少时多实例子项BLOCKED。

**业务步骤**：
1. 按DS-TX在平台查看组织树，共100次真实查询，分别落在neocat-a与neocat-b；90次成功、10次独立未登录访问被拒。对照台账等待本批分析完成，不以页面点击数代替实际请求数。
2. `it.dev` 登录，打开服务列表，选择对应时间范围和Transaction类型，点击 `neocat-backend`。
3. 在Type列表找到URL，点击URL进入Name列表，再点击 `GET /api/orgs`。
4. 查看默认Hits趋势，切换失败量、失败率、平均耗时，再分别筛选neocat-a、neocat-b与全部机器。
5. 返回Name列表，打开该行最近调用取样，点击一条已记录标识的请求。
6. 在Trace页展开本地调用节点，再返回原报表，确认服务、范围与目标未错位。

**功能预期**：服务自动出现；Type只进入Name列表，Name进入趋势；默认全机器Hits；取样能定位到正确请求树，节点可展开，返回后筛选不串目标。

**数据预期**：100次、失败10次、失败率10%；A为80次/4失败、B为20次/6失败。耗时/分位按100条真实测量台账计算，不套用180ms。趋势各桶之和100；取样来自所选范围及目标，最多最近30条；Trace服务、实例、状态、时间及实际SQL/内部节点与选中请求相符，无其他请求串树，不含凭据。接收成功但无可核对报表不能判通过；固定耗时算术另按DS-TX-BOUND核查。

## K03 自身组织事件与异常/慢调用定位

**目的**：从业务异常或性能问题定位到对应调用。**追溯**：链路18、19。

**前置与数据**：DS-EVENT、DS-PROBLEM；平台使用默认慢阈值。

**业务步骤**：
1. 在平台的专用父组织下完成36次合法创建、4次同父重名拒绝，生成DS-EVENT；另在独立窗口按DS-PROBLEM准备真实异常及慢阈值受控变体，两类证据分开。
2. 登录，选择 `neocat-backend` → Event → organization → node-create，查看Hits、失败率和QPS。
3. 在同服务的对应窗口进入Problem，依次点击异常、慢请求、慢SQL、慢调用、慢缓存；没有实际调用或缺受控能力的子项登记BLOCKED，不编造外部依赖。
4. 在异常列表查看相同异常名的聚合，再打开取样查看两条不同完整消息。
5. 在慢请求中选失败且超阈值的URL，查看趋势和取样，打开Trace定位到同一次失败请求。

**功能预期**：Event无耗时分位；Problem提供五类；异常按异常名、慢类按Transaction Name；同一调用可以进入异常和慢类。

**数据预期**：Event40次、失败4、失败率10%；仅36个新节点，4次拒绝不新增组织。受控阈值等值及以下不归慢，超阈值归对应类；两条同名异常合计2次，消息分别保留且脱敏。失败慢URL在两类各一次；真实观测与受控记录不混算，控制台WARN本身不替代Event/Problem产物。

## K04 自身 JVM 与成员数 Metric 健康诊断

**目的**：区分JVM状态观测与业务指标观测，完成从总览到实例/标签的诊断。**追溯**：链路20、21。

**前置与数据**：DS-JVM真实采样、DS-METRIC基础10次成员变更观测；自身Heartbeat及成员数Metric已接通，不混入受控JVM/高基数扩展或其他成员操作。

**业务步骤**：
1. 等平台两个后端JVM各自完成至少两次实际采样；按DS-METRIC在平台组/采集组副本进行10次成员变更，并保留实际有效人数台账。
2. 打开 `neocat-backend` → Heartbeat，查看堆、GC、线程，分别选择neocat-a、neocat-b；打开指标旁说明。
3. 打开同服务Metric，在总览查看neocat.org.effective_members小图，点击标题或“查看详情”。
4. 在详情选择org=平台组，再增加membership=direct；清空筛选回到全量。
5. 返回总览再进入详情，核对时间范围及保存在详情地址中的标签条件。

**功能预期**：Heartbeat按实例展示，不把JVM指标拼成一个总量；Metric总览默认全量count单曲线，详情筛选后仍单曲线，清空恢复全量。

**数据预期**：JVM按各自实际台账显示桶内最后采样，不合并两个JVM、不要求固定内存/线程数；Metric全量count10、平台组/direct为8，不把sum55当count。Metric值对应有效人数1至10，未上报字段显示缺口不补0。固定JVM值及缺字段边界另按DS-JVM-BOUND验收。

## K05 隔离自身运行态依赖 → 跨服务 Trace

**目的**：定位服务调用关系，并区分“依赖已观测”与“下游树未收到”。**追溯**：链路22、Trace组装。

**前置与数据**：DS-DEP，同一平台后端构件的隔离上/下游角色运行态及真实只读调用可用；每次调用有Trace根标识，7次完整、3次缺下游。普通单体部署无此能力时本例BLOCKED，不另建业务服务，不拿模块/SQL调用冒充跨服务。

**业务步骤**：
1. 在隔离自身运行态内发起10次实际组织只读查询，其中2次被拒；按约定仅保留7次下游树，并记录上游实际远程耗时。
2. 打开neocat-self-upstream依赖页，在下游点击neocat-self-downstream，查看服务对趋势。
3. 切到neocat-self-downstream依赖页，查看上游neocat-self-upstream。
4. 打开一次完整请求的代表性Trace，展开两个自身运行态的本地树。
5. 再打开一次缺下游请求的Trace，查看缺失位置与已有节点。

**功能预期**：依赖以列表为入口，方向正确；完整Trace可展开两棵树；部分Trace显示明确缺失而不丢整条请求。

**数据预期**：双向视图都对应同一10次调用、2次失败、20%，Avg从上游真实远程耗时台账计算；不是7次或17次。完整请求各树独立参与对应服务身份统计；缺下游3次仍计依赖，不伪造下游观测。仅重放关联树通过不能证明实际上下文传播通过。

## K06 组织成员 → 大盘 → 指标卡片

**目的**：让有资格的成员建立可持续查看的业务大盘。**追溯**：链路24、25。

**前置与数据**：DS-ROLE、DS-TX；it.dev有订单组成员资格（组织名不表示外部系统）；准备大盘名 `it-平台健康`，目标neocat-backend/URL/GET /api/orgs，公式failures / hits、阈值线“高于0.05”、范围W。

**业务步骤**：
1. it.dev打开“大盘”，选择订单组，填写名称并创建大盘。
2. 进入大盘，选择目标服务和指标对象，填写公式、范围及阈值线，点击“保存卡片”。
3. 点击卡片查看趋势，进入机器维度依次查看neocat-a、neocat-b，再返回全部机器。
4. 离开大盘再进入，刷新页面；由祖先成员it.parent打开同一大盘。
5. it.outsider尝试从列表和已知大盘地址访问同一对象。

**功能预期**：成员与祖先成员可查看/编辑；非成员看不到内容且不能绕过入口。卡片保持单一指标，阈值线可见，机器诊断不改变默认全量目标。

**数据预期**：仅新增一个订单组大盘、一张卡片及对应阈值线；全量结果0.1、A为0.05、B为0.3；读回公式、目标、范围和阈值线不丢失。拒绝访问不创建额外资源。

## K07 服务告警 → 预告警 → 手动启用 → 关闭

**目的**：完成主动发现故障的规则生命周期。**追溯**：链路26、28、29、30。

**前置与数据**：DS-ALERT；it.outsider普通账号，接收人it.receiver；真实规则评估和分发诊断可观察。无需外部接收服务；通道选择需要配置时使用隔离记录型适配器及非真实凭据，未具备则对应运行子项BLOCKED。真实送达仅A18可选专项。

**业务步骤**：
1. 打开“告警规则”，选择服务告警、neocat-backend/URL/GET /api/orgs、Hits > 10、X=3、接收人及隔离通道路由。
2. 通过平台组织查询准备12/13/14的历史完整点，点击“预览（试算）”，确认显示会触发且没有正式评估/分发副作用。
3. 点击“保存”，返回规则列表；刷新确认关闭，没有分发尝试。
4. 点击“启用”，从下一个完整分钟开始通过自身操作及受控缺口产生DS-ALERT m1至m10。
5. 对照实际规则评估、接收人数、通道路由和分发尝试/失败；m10评估完成后点击“关闭”，继续产生三个满足点。
6. 重新进入规则列表，确认关闭状态与配置仍保留。

**功能预期**：预览不分发，保存不启用，启用后按新点建窗；关闭后不触发。记录型路由只证明分发意图；UnsupportedExternalNotifier仅证明失败，不算送达。只看预览不算运行规则通过。

**数据预期**：一条服务规则，窗口3、阈值10、接收人与通道准确；m3、m4、m9、m10触发，其他点不触发；启用前历史不填窗；m6缺数不是0。关闭后新增满足点不发送，不产生站内触发历史。

## K08 卡片 → 组织告警 → 公式变更联动

**目的**：验证组织成员能以卡片结果监控业务，且公式变化不会沿用旧判定。**追溯**：链路27、28、31。

**前置与数据**：K06卡片副本；it.dev操作；接收人it.receiver为订单组有效成员；以failures / hits > 0.05、X=3创建规则，之后改为hits - failures，业务单位变化时同步重新配置比较阈值。

**业务步骤**：
1. 点击卡片“一键创建组织告警”，核对订单组、卡片目标及当前公式已带入。
2. 选择有效成员接收人，填写条件和窗口，预览后保存，回列表确认关闭。
3. 手动启用，在后续完整分钟按已记录比例进行平台组织查询，产生三点满足条件的数据；观察实际判定及分发打点，不要求外部接收端。
4. 返回大盘编辑该卡片公式并保存，重新打开关联规则。
5. 核对规则跟随新公式、已关闭；按新结果口径调整阈值，保存并再次手动启用。
6. 仅观察再次启用后的完整点，确认必须重新积累窗口。

**功能预期**：目标真实带入，不是只出现“已复制”提示；成员资格受限；公式变化关闭关联规则，不能继续用旧公式触发。

**数据预期**：规则始终关联同一卡片和订单组；DS-TX范围内原公式0.1、改后90，运行分钟另按当分钟真实台账计算，不能把W汇总当每分钟结果。旧窗口不沿用，阈值不被阈值线覆盖。保留读回及运行评估证据；真实送达另见A18可选专项，未测不判通过。
